# 引き継ぎ仕様書: 予約の承認フロー自動化

> **✅ 2026-06 実装済み**（`google-apps-script/reservation.gs` の「承認フロー」セクション）。
> Meet URL の生存確認は妥協案（固定URL＋オーナーへの確認リマインド通知）を採用。
> 運用方法は `docs/reservation-form-setup.md` の「日々の運用」を参照。

このドキュメントは、予約システムに「承認 → 確定案内の自動化」を追加実装するための仕様書。
実装前に必ず `CLAUDE.md` と `docs/reservation-form-setup.md` を読むこと。

---

## 現状のシステム（2026-06 時点・稼働中）

```
reserve.html（予約フォーム）
    ↓ POST
GAS ウェブアプリ（google-apps-script/reservation.gs が参考コピー。実体はオーナーのGASプロジェクト「予約受付」）
    ├─ スプレッドシート「予約受付」シートに記録（14列）
    ├─ Google カレンダーに【仮】イベント作成
    ├─ オーナーに LINE（Messaging API push）+ メール通知（2アドレス）
    ├─ お客様に受付確認メールを自動返信（「確定前」と明記）
    └─ ?action=availability で空き状況API（フォームの日時選択肢に使用）
```

- 予約は**前日予約制**（当日は受け付けない。`LEAD_DAYS = 1`）
- 「対応状況」列（13列目）が空のまま3時間経つと、LINEに未対応リマインドが飛ぶ
  （`checkUnhandledReservations`、1時間ごとの時間トリガー）
- **現在、確定のご連絡はオーナーがメールを手書きしている。ここを自動化したい。**

### シート列構成（1始まり）

| # | 列名 |
|---|------|
| 1 | 受付日時 |
| 2 | お名前 |
| 3 | 性別 |
| 4 | 生年月日 |
| 5 | 出生時間・出生地 |
| 6 | メール |
| 7 | コース |
| 8 | 第一希望 |
| 9 | 第二希望 |
| 10 | テーマ |
| 11 | ご相談内容 |
| 12 | 支払い希望（PayPay / 銀行振込 / 現地払い（対面）） |
| 13 | 対応状況 |
| 14 | リマインド |

## 作りたいもの：承認フロー

**トリガー**: オーナーがスプレッドシートの「対応状況」列に「**確定**」と入力する
（スマホのスプレッドシートアプリからも操作できることが要件）

### A. オンライン予約の場合（コース列に「オンライン」を含む）

「確定」と入力されたら**全自動**で確定案内メールをお客様に送信する。

メールに含める内容：
1. 確定した日時・コースの確認
2. **Google Meet の URL**
3. **お支払いのご案内**（12列目の支払い希望に応じて出し分け）
   - PayPay → PayPay ID
   - 銀行振込 → 振込先口座
   - ⚠️ PayPay ID・口座情報は**リポジトリにコミットしない**。GASエディタ上の CONFIG にのみ記入させる構成にする（プレースホルダで実装し、設定手順をドキュメントに書く）
4. 支払い期限・キャンセル連絡の方法など定型文

**Meet URL の生存確認もしたい**（オーナー要望）：
- 固定 Meet URL を使う場合、`UrlFetchApp` で HTTP 200 を確認する方法は不完全（無効な会議コードでもページ自体は返る）
- 推奨: **Calendar API（拡張サービス）で会議付きイベントを生成**し、予約ごとに新しい Meet リンクを発行する方式。これなら「リンク切れ」自体が起きない
- 実装が重ければ妥協案: 固定URLを使い、確定メール送信後にオーナーへのLINE通知に「Meet URLの動作確認をしてください」と一文添える

送信に**成功したときだけ**「対応状況」を「案内済み」に自動更新する。
失敗したら LINE + メールでオーナーにエラー通知（黙って失敗しないこと。これ最重要）。

### B. 対面予約の場合（コース列に「対面」を含む）

自動送信は**しない**（待ち合わせ場所は毎回オーナーが決めるため）。

「確定」と入力されたら：
1. **Gmail に下書きを自動作成**する（`GmailApp.createDraft`）
   - 宛先・件名・本文テンプレートまで全部入り
   - 場所だけ `【★待ち合わせ場所をここに記入★】` のプレースホルダにしておく
2. オーナーの LINE に「対面予約の確定下書きを作りました。Gmailの下書きから場所を記入して送信してください」と通知
3. オーナーは Gmail アプリで下書きを開き、場所を埋めて手動送信
4. 送信後、オーナーが「対応状況」を「案内済み」に手で更新する運用

### 共通の注意

- 「確定」入力の検知は **インストーラブル onEdit トリガー**を推奨
  （シンプルトリガーの onEdit ではメール送信権限がないため不可）
  - 保険として、1時間ごとの既存トリガー（または新設の時間トリガー）で「確定のまま未処理」の行を拾う二重化が望ましい
- 同じ行で二重送信しないこと（「確定」→処理済みなら「案内済み」に変わるので、「確定」のままの行だけ処理する設計で自然に防げる）
- 既存のリマインド機能との整合: 「対応状況」に何か入っていればリマインドは止まる（既存実装のまま）
- カレンダーの【仮】イベントのタイトルを「【確定】」に更新できると望ましい（任意）

## 壊してはいけないもの

1. `?action=availability`（フォームの空き状況API）と `doPost`（予約受付）の既存動作
2. シートの列構成。列を増やす場合は末尾に追加し、`SHEET_HEADERS` と列番号定数を同期する
3. **トークン・PayPay ID・口座情報・個人情報をリポジトリにコミットしない**
   （`reservation.gs` のリポジトリ側コピーは CONFIG が空の状態を保つ）
4. お客様向け文面に LINE への誘導を入れない（LINE予約は廃止済み。問い合わせ先はメールのみ）
5. 変更後は GAS の「デプロイを管理 → 新バージョン」での再デプロイが必要（オーナーに案内すること）

## テスト手順（実装後）

1. フォームからテスト予約（オンライン・PayPay希望）→ シートの対応状況に「確定」と入力 → 確定メールが自動で届き、対応状況が「案内済み」になること
2. 銀行振込希望でも同様に確認（文面の出し分け）
3. 対面でテスト予約 → 「確定」入力 → Gmailに下書きができ、LINEに通知が来ること。自動送信されて**いない**こと
4. メール送信を意図的に失敗させ（宛先を不正にする等）、エラーがLINEに通知されること
5. テストで作ったシート行・カレンダーイベント・下書きを削除
